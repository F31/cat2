# 开工前置决策清单（p0 #13 五角色 / #16 佣金 / #3 AI 等）

> 面向**产品 / 运营 / 财务**的拍板清单。每一项给出：**待决问题 → 预研建议 → 影响面 → 不拍板的后果**。
> 用途：本清单签署后，`p4-channel-admin`（运营商/渠道/RBAC/佣金/结算）与 `p5-ai-scenarios` 剩余部分可立即开工。
> 依据：`docs/prd-trace/pending-confirmations.md`、`docs/modules/channel-预研.md`、`docs/adr/ADR-001-channel-data-model.md`、`openspec/changes/p4-channel-admin/tasks.md` §1–3。
> 签署规则：每项填「结论（采纳建议 / 改为…）/ 决策人 / 日期」；采纳后由研发把对应 ADR 状态由「提议」转「采纳」。

## 0. 为什么现在必须先定

- p4 的非阻塞部分（治理 §4、审计 §5、认证 §6、看板/埋点/导出 §7）**已完成并通过全量回归**；`§1–3`（运营商/渠道后台、五角色 RBAC、佣金结算）因 **#13** 未确认而**未开工**。
- 剩余工作几乎全部落在「谁能操作什么、钱怎么算、谁复核」这类**业务口径**上——代码框架（settings/审计/状态机/事件/导出）已就绪，无需新增内核能力。
- **不拍板 = 上线合规与验收缺口**：p6 退出标准 §8.1（达到 PRD 11.4）含运营商/渠道后台条目，无法判定完成。

## 2. D1 详解：后台五角色与权限点（#13）

### 2.1 待决问题

1. **角色集合**是否采用「超管 / 运营 / 审核员 / 财务 / 渠道经理」五角色？
2. **后台账号模型**：是否引入独立 `sys_admin_user` / `sys_admin_role`（与小程序用户分离），还是沿用 `idn_user.admin_role` 扩展为一对多角色？
3. **数据范围**：角色是否带 `space_id`（门店/区域）？渠道经理是否按 `region_code` 过滤？
4. **登录安全**：后台是否强制**二次验证**（TOTP 或短信）？是否限定 IP？
5. **双人复核清单**：哪些操作强制「复核 ≠ 执行」（会员人工调整、退款、结算打款、改价格/佣金比例、导出）？
6. **敏感操作二次确认**清单是否与上表一致？

### 2.3 影响面（若采纳）

- **表**：新增 `sys_admin_user` / `sys_admin_role`（含 `space_id`）迁移与五角色种子；`sys_` 内核表放 `adapters/pg` KernelTables。
- **内核**：`policy` 增「复核 ≠ 执行」互斥规则（违反 `denied` 记审计）；现存 `requireAdmin` 升级为权限点校验。
- **契约**：admin.yaml 全量路径标注权限点；`contracts` 登记权限点清单；后台登录 `denied` 审计（防爆破）。
- **前端**：admin-web shell 按 RBAC 过滤菜单（菜单级 + action 级按钮可用性）；后台强制二次验证。
- **测试**：五角色 × 权限点全量表驱动用例（含负向）；`tests/audit` 覆盖面对齐 `p4 §9.4`。
- **工作量**：见 `channel-预研.md` §6，RBAC 单独约 **1.5 人天**，其余 §1–2 约 **3 人天**、§4–8 约 **5.5 人天**。

### 2.4 不拍板的后果

- `channel`（运营商/渠道/佣金/结算）与 RBAC 无法开工；p4 §1–3、§9.1/§9.3、§10.1 持续挂起，p6 §8.1 无法判定完成。
