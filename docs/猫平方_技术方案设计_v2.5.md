# 猫平方商业一体化综合服务平台 · 技术方案设计 v2.5

版本:v2.5(在 v2.0 基础上,重点补强**模块边界、分层解耦、共享复用、工程结构**) | 依据:《产品需求说明书 v2.5》(一期唯一依据)、《猫平方 6 方合作服务平台需求概要》(战略方向参考)、《技术方案设计 v2.0》 | 编制日期:2026-10-12 | 适用对象:研发 / 架构 / 项目管理

## 0. 结论先行

**v2.0 的主体判断保留**:模块化单体、必选依赖只有 PostgreSQL 与对象存储、其余能力走「端口 + 适配器」、AI 可选可降级、规则即数据、状态机显式化、安全默认开启。这些在 v2.5 不再重复论证,只在需要处简述。

**v2.5 解决 v2.0 留下的四个问题**:

1. **模块边界靠约定,不靠机制**:v2.0 只写了「禁止跨模块读表」,靠 lint 兜底;模块粒度也不均匀(`content` 同时装了四类内容、搜索、收藏关注;`profile` 同时装了名片、认证、核验、字典;`trade` 把「钱」和「会员/佣金的业务含义」混在一起)。
2. **「共享复用」只覆盖技术层**:v2.0 有 `kernel / ports / adapters`,但字典与标签、实体引用、媒体、配额、通知、审核这类**业务通用能力**没有归属,最终会被各模块各写一份;前端(小程序、后台)的共享更是空白。
3. **工程结构缺少多端与聚合层**:没有小程序/后台/契约的工程组织,没有跨模块「读聚合」的位置,导致详情页、首页这类聚合接口要么破坏边界、要么堆进某个模块。
4. **没有对齐《需求概要》的战略方向**:概要提出「大学/商协会/政府服务机构等可独立部署、共享用户与数据、拥有自己的后台与内部数据」「行业性质、合作需求通用标签」「所属单位及单位确认(可多家)」「官方合作认证」。v2.0 写的是「PRD 并非 SaaS 多租户」,**对一期成立,对产品方向不成立**,需要预留而不是排除。

| 你的要求 | v2.5 的设计手段 | 章节 |
| --- | --- | --- |
| 1 工程目录:业务模块拆分与边界 | 17 个模块(15 个业务模块 + 2 个共享业务域)按七级**依赖阶梯**组织(只能向下依赖);Go `internal` 由**编译器**强制边界;`contract` 包是唯一对外面;表前缀 + sqlc 校验杜绝跨模块读表 | 第 4、6 章 |
| 2 分层解耦 + 业务/通用组件共享复用 | L0~L3 四级共享体系;「向上只用事件或注册表」的通信规则;9 类扩展点注册表;业务共享域(字典标签、实体引用、媒体、配额);前端同构共享 | 第 5 章 |
| 3 其他应纳入的内容 | 多站点(SaaS)预留、通用标签体系、内容类型插件、猫立方项目与平台项目的数据模型、后台 RBAC、事件目录、PRD 追溯矩阵、研发规范与新增模块清单 | 第 4.8、7~13 章、附录 |

## 2. 设计原则

沿用 v2.0 六条(先单体后拆分、依赖做减法、规则即数据、状态机显式化、AI 可选可降级、安全默认开启),新增以下五条,用于约束模块边界与复用:

1. **依赖只向下**:模块分阶梯,低阶不得 import 高阶。向上通信只有两种方式:**事件**(低阶发布、高阶订阅)与**注册表**(高阶把实现注册进低阶开的口子)。
2. **一个事实只有一个 owner**:每张表只属于一个模块;其他模块要数据,走契约或订阅事件,**不 JOIN、不读表**。
3. **引用,不复制**:圈子挂载内容、猫立方关联项目、收藏、关注、举报都用 `EntityRef{type,id}` 指向原实体(与 PRD 5.12.5、5.6.8 同构)。
4. **共享先找下层**:要复用的东西,放到能被所有使用者依赖的**最低一层**;不得为了复用而让低阶依赖高阶。判定见 5.5「放哪里」决策树。
5. **机制优于约定**:能用编译器、CI、类型系统强制的边界,不用文档约定。

### 3.1 五层结构

### 3.2 技术选型

v2.0 的选型表(Go + PostgreSQL + 可选 Redis、Outbox + PG 任务表、PG 检索 → 可换 Meilisearch/ES、不引入 Consul/Nacos/Kong/Argo、OpenTelemetry)**全部沿用**。v2.5 把 v2.0 中「二选一」的几处**定下来**,避免团队各自理解:

| 决策点 | v2.0 | v2.5 决定 | 理由 |
| --- | --- | --- | --- |
| 数据访问 | pgx+sqlc 或 GORM 二选一 | **pgx + sqlc** | 查询是显式 SQL,可以静态检查「只访问本模块表前缀」;无反射魔法,便于以后拆库 |
| 小程序框架 | 原生或 Taro | **Taro + React + TypeScript** | 与后台(React)共享 TS 类型、请求客户端、校验与权限提示逻辑;原生仅作为插件兼容性不足时的回退 |
| 前端仓库 | 未定 | **pnpm workspace monorepo** | 小程序、后台、共享包同仓,契约变更一次改全 |
| 主键 | 未定 | **int64(时间有序,应用侧生成)**,JSON 中一律输出为**字符串** | JS 数字只有 53 位精度,直接输出会丢位 |
| 金额 | 未定 | **int64 分**;折扣系数 `numeric(6,4)`,统一舍入规则(四舍五入到分,规则入配置) | 避免浮点误差 |
| 时间 | 未定 | 库内 `timestamptz`(UTC);业务「自然日」(配额、通知合并)统一按 **Asia/Shanghai** | 配额与合并口径一致 |
| 契约 | OpenAPI | OpenAPI 3(HTTP)+ **事件 JSON Schema**(进程内事件与未来 MQ 共用) | 事件也是契约 |

## 4. 模块化设计:拆分与边界

### 4.1 模块地图

模块分三组,共 **17 个**(含 2 个共享业务域)。注意:这是**代码包的边界,不是服务的边界**,一期仍然是一个二进制。

**A. 共享业务域(shared,被几乎所有业务模块依赖,自身不依赖业务模块)**

| 模块 | 职责 | 对应 PRD |
| --- | --- | --- |
| `dict` | 字典与标签:taxonomy(行业、区域、需求/供给、行业性质…)、**主体类型配置**、画像字段模板、`TagSet` 通用标签;只停用不删除 | 6.4、8.2、8.6 |
| `media` | 文件上传、图片处理与缩略图、对象存储引用、引用计数与孤儿清理 | 8.9.2 |
| `entityref`(轻量包,无独立表) | `EntityRef{type,id}` 与解析器注册表(给定引用,返回标题/封面/状态/可见性) | 5.12.5、5.6.8 |

**B. 基础域(R0,无业务依赖)**

| 模块 | 职责 | 对应 PRD |
| --- | --- | --- |
| `identity` | 微信登录、手机号、会话与令牌、`authz_ver`、账号状态、注销与匿名化 | 5.1、10.4.3 |
| `trust` | 内容安全 `Moderation` 端口、举报、违规记分、封禁、审核任务队列(统一)、敏感词/引流词 | 9.3、6.6、11.1 |
| `ai` | LLM/Embedding/OCR/ASR 网关、提示词版本、配额、降级(可选装载) | v2.0 第 7 章 |

**C. 业务域**

| 阶 | 模块 | 职责 | 对应 PRD |
| --- | --- | --- | --- |
| R1 | `profile` | 个人/组织名片、三层画像、对外展示设置、名片分享、主体类型实例、画像完成度 | 5.11.3、8.1、9.1 |
| R1 | `msg` | 会话、消息、未读(序号−游标)、增量同步、群聊成员解析(注册表) | 5.5、9.5 |
| R1 | `trade` | **只管钱**:订单、支付、退款、对账、分摊认筹(多笔支付合并成一单);不认识「会员」「订阅」 | 8.3.1 |
| R1 | `social` | 关注/粉丝/收藏(目标是 `EntityRef`),不做排行榜 | 5.10 |
| R2 | `verify` | 实名/个人/企业/机构认证、身份核验、组织管理员、一人多单位关系、认证 `Badge` | 5.7、5.8、8.4、9.2 |
| R2 | `content` | 项目/产品/会议/活动(`ContentKind` 插件)、状态机、产品库、详情 | 5.4、5.9、6.3、8.5 |
| R3 | `membership` | 会员等级与权益、企业版与子账号、到期回落、会员权重(向 discovery 输出等级) | 5.11.5、8.3.1 |
| R3 | `cube` | 猫立方空间/成员/关于我们/订阅档位、猫立方内项目、研究记录、任务、报备、邀请 | 5.6、8.7 |
| R4 | `circle` | 圈子、圈内需求/动态、挂载引用、公告、邀请、「到猫立方里办」 | 5.12 |
| R4 | `channel` | 运营商身份、渠道管理、佣金流水、结算单、保底任务、保证金台账 | 6.7、7.x |
| R5 | `discovery` | 事业线卡片流、搜索、匹配(候选预计算、解释理由);自建读模型 | 5.2、5.3、9.1 |
| R6 | `notice` | 通知中心:事件 → 模板 → 站内通知/订阅消息;订阅授权额度;圈内日结合并 | 5.5.4、11.3 |

**运营后台(admin)不是模块**,是接入层的 BFF:每个模块在自己目录下提供 `admin/`(路由 + 菜单声明),由 admin 应用按角色组装(6.1)。

**板块名与模块的映射**(产品命名与代码边界解耦):

| 产品板块 | 对应模块 |
| --- | --- |
| 事业线(概要:合作广场) | discovery + content + profile + social |
| 圈子(概要:猫平方) | circle + content(挂载/活动/会议);圈子不做聊天(PRD 1.6「两处聊天」),因此不依赖 msg |
| 猫立方 | cube + msg(群聊)+ trade(订阅/分摊);猫立方订阅档位归 cube 自己管理,与 membership(个人会员)互相独立 |
| 消息 | msg + notice |
| 我的 / 认证 / 会员 | profile + verify + membership + trade |
| 总管理后台 | admin(聚合所有模块的 `admin/`) |

### 4.2 依赖阶梯与通信规则

**规则一:模块只能依赖编号更低的阶(同阶也不可)**,CI 用本表生成的依赖规则校验。

| 阶 | 模块 | 允许依赖(仅其 `contract`) |
| --- | --- | --- |
| R0 | identity、trust、ai | shared、kernel |
| R1 | profile、msg、trade、social | R0、shared |
| R2 | verify、content | R0、R1、shared |
| R3 | membership、cube | R0~R2、shared |
| R4 | circle、channel | R0~R3、shared |
| R5 | discovery | R0~R4(只依赖其**事件类型**) |
| R6 | notice | R0~R5(只依赖其**事件类型**) |

**规则二:向上通信只有两种方式**

| 方向 | 方式 | 举例 |
| --- | --- | --- |
| 低阶 → 高阶(「发生了什么」) | **领域事件**:低阶发布,高阶订阅(高阶 import 低阶的 `contract/events`) | `OrderPaid`(trade, R1)→ membership(R3)开通会员 |
| 高阶 → 低阶(「怎么做」) | **注册表**:低阶开口子(interface),高阶启动时把实现注册进去 | cube(R3)向 msg(R1)注册「猫立方群聊成员解析器」;content/msg/circle 向 trust(R0)注册「审核对象提供者」;membership/cube 向 trade 注册「订单履约器」 |

这样低阶永远不知道高阶的存在,依赖图无环,抽出任何一个模块都不会牵连上层。

**规则三:读聚合只放在 `bff`**。详情页要同时展示「名片(profile)+ 认证标识(verify)+ 会员等级(membership)+ 是否已关注(social)」,这是一次**只读**聚合,放在 `bff/miniapp`,由它依赖这几个模块的 `contract`。模块自身的 domain 层不得为了展示去调用别的模块。

**规则四:跨模块写操作不用分布式事务**。一个业务动作若需要多个模块各自改数据,采用「本地事务 + Outbox 事件 + 订阅方幂等」的最终一致;必须强一致的场景(分摊成团开通)限定在**同一模块内**完成(见 8.4)。

### 4.4 数据归属与访问规则

- **表前缀即归属**:每张表以模块前缀命名,**一个前缀只能被其所属模块的 `internal/infra` 访问**。

| 模块 | 前缀 | 模块 | 前缀 |
| --- | --- | --- | --- |
| identity | `idn_` | verify | `vfy_` |
| trust | `trs_` | content | `cnt_` |
| ai | `ai_` | membership | `mbr_` |
| dict | `dct_` | cube | `cub_` |
| media | `med_` | circle | `cir_` |
| profile | `prf_` | channel | `chn_` |
| msg | `msg_` | discovery | `dsc_` |
| trade | `trd_` | notice | `ntc_` |
| social | `soc_` | 内核 | `sys_`(配置、outbox、任务、审计、配额、特性开关) |

- **sqlc 校验**:构建时解析每个模块 `infra/queries/*.sql`,出现非本模块前缀的表即失败(CI 脚本 `tools/archcheck`)。
- **跨模块外键**:不建数据库外键,只存对方 ID(与 `EntityRef` 一致);引用完整性由事件与定期巡检保证。这样将来某个模块拆库不需要动 schema。
- **只读副本投影**:`discovery` 的 `dsc_search_doc`、`dsc_match_candidates` 是**投影**,可随时由事件回放重建,不是事实来源。
- **迁移**:每个模块自己的 `migrations/` 目录,内核迁移器按 `DependsOn` 拓扑顺序执行;遵循 expand → migrate → contract。

### 4.5 契约:contract、事件、注册表

**contract 包只放三类东西**:`Facade` 接口 + 入参出参 DTO、领域事件类型、注册表接口(开口)。不放实现、不放模型、不放 SQL。

**事件规范**

| 项 | 规范 |
| --- | --- |
| 命名 | 过去式、`模块.事件`,如 `trade.OrderPaid` |
| 载荷 | 事件 ID、`occurred_at`、版本号 `v1`、`space_id`、业务字段;**不含手机号、证件号等敏感字段** |
| 投递 | Outbox 同事务写入、至少一次;订阅方以事件 ID 幂等 |
| 演进 | 只加字段不改义;破坏性变更发 `v2` 并双发一个周期 |
| 契约 | 每个事件有 JSON Schema(`contracts/events/`),CI 校验生产方与订阅方一致 |

完整事件目录见附录 C。

**扩展点注册表(9 类)**:模块启动时(`Register`)把实现挂进去,**注册即生效,删除模块即失效**。

| # | 注册表 | 谁开口 | 谁注册 | 作用 |
| --- | --- | --- | --- | --- |
| 1 | `ReviewSubjectProvider` | trust | content、msg、circle、profile、verify | 告诉审核系统「怎么取这类对象的文字/图片」「审核结论怎么落回去」 |
| 2 | `OrderFulfiller` | trade | membership、cube | 按 `biz_type` 履约:支付成功后开通会员/订阅 |
| 3 | `SessionMemberResolver` | msg | cube | 群聊会话的成员由谁决定(猫立方成员表) |
| 4 | `EntityResolver` | entityref | profile、content、circle、cube | 给定引用返回展示信息与可见性(收藏、关注、举报、挂载都用) |
| 5 | `ContentKind` | content | content 自身(项目/产品/会议/活动)、未来新类型 | 字段 schema、校验、卡片字段、审核文本提取 |
| 6 | `CapabilityProvider` | kernel/policy | identity、membership、verify、cube、trust | 组装 `Actor`(是否已实名、会员生效、猫立方角色…) |
| 7 | `PolicyRule` | kernel/policy | 各模块 | 每个模块自己的动作与规则,PRD 权限矩阵每格对应一条 |
| 8 | `NoticeTemplate` | notice | 各模块 | 事件 → 通知文案/渠道/合并规则 |
| 9 | `AdminSection` | admin(接入层) | 各模块 | 后台路由与菜单,由 RBAC 过滤 |

另有两个**声明式注册**(不是接口,是数据):`StateMachineDef`(状态机)、`SettingsSchema` + `QuotaDef`(配置项与限额,后台据此自动生成配置界面)、`SchedulerJob`(到期转态)。

### 4.6 边界强制手段(从强到弱)

| 层级 | 手段 | 防什么 |
| --- | --- | --- |
| 编译器 | 模块实现放 `modules/<m>/internal/...`,Go 规定只有 `modules/<m>/` 子树内的代码能 import | 别的模块 import 你的 domain/infra |
| CI | `tools/archcheck`:① 依赖阶梯 ② sqlc 表前缀 ③ 非 infra 层使用 `database/sql`/`pgx` ④ `bff` 不得调用任何模块的写接口(只读聚合) | 违反阶梯、读他人表、绕过仓储 |
| CI | 契约测试:事件 Schema 与 OpenAPI 的生产方/消费方一致 | 悄悄改字段 |
| 评审 | `CODEOWNERS`:每个模块目录指定 owner;`contract/` 变更必须 owner 审批 | 契约被随手改 |
| 运行时 | `ScopedRepo` 强制注入 Scope;敏感字段 `Visible[T]` 默认不输出 | 越权读、漏脱敏 |

### 4.7 拆分判据

| 判据 | 说明 |
| --- | --- |
| 触发条件(满足其一) | 独立伸缩需求(长连接、AI 推理)、独立发布节奏、独立合规隔离(资金)、团队规模需要独立 ownership |
| 候选与顺序 | `msg`(二期 WebSocket)→ `ai` → `discovery`(搜索切 ES/Meili)→ `trade`(资金隔离审计) |
| 拆分动作 | ① 该模块 `contract` 的 Facade 由进程内实现换成 gRPC/HTTP 客户端适配器 ② 事件总线换 NATS/RabbitMQ ③ 数据库按表前缀迁出。**业务代码不动** |
| 不拆 | `identity`、`dict`、`profile`、`verify`、`content`、`cube`、`circle`:耦合高、体量小,拆了得不偿失 |

### 4.8 多站点(SaaS)预留

**一期结论:不实现,只预留。** 预留成本约为「几列、一个上下文对象、一个配置层级」,远低于以后补。

概要的要求翻译成技术语言:**「站点 Space」= 一个机构(大学/商协会/政府服务单位…)在平台上的运营空间**,具备:自己的管理员与后台、自己的内部数据、与主站**共享用户和部分数据**。

| 预留项 | 一期做法 | 以后(M1)怎么用 |
| --- | --- | --- |
| `SpaceContext` | 所有请求携带 `space_id`,一期恒为 `1`(主站);进入 `ScopedRepo` 与事件载荷 | 按域名/入口/小程序码识别站点 |
| 数据归属列 | 仅下列表加 `owner_space_id smallint default 1`:`prf_org`、`cnt_item`、`cir_circle`、`cub_cube`、`sys_settings`、后台账号 | 站点内数据按此隔离 |
| 可见性 | 内容/圈子/猫立方带 `visibility`(`platform` / `space`),一期恒为 `platform` | `space` = 仅本站点成员可见(「内部服务数据」) |
| 用户 | 用户全局唯一;预留 `idn_space_member(user_id, space_id)` 的位置,一期不建表 | 一个用户可属多个站点,用户与主站数据共享 |
| 配置 | `settings` 带 `scope`(platform / space:<id>),取值顺序:space → platform | 站点自定义品牌、限额、字段模板 |
| 后台 | RBAC 角色带 `space_id` | 站点管理员只能管本站点 |

**演进三步**:M0 一期预留 → M1 逻辑多站点(同库,按 `space_id` 隔离,机构获得自己的后台入口与品牌)→ M2 物理独立部署(机构要求数据落在自己机房时,用开放 API + Webhook 做联邦同步,**非一期目标,且会显著增加复杂度**)。多数机构需求 M1 即可满足,建议产品先确认「独立部署」的真实含义(数据主权要求 vs. 独立后台与品牌),见第 14 章待确认项。

## 5. 共享与复用体系

### 5.1 四级共享

复用的原则是「放到能被所有使用者依赖的最低一层」。四级从低到高:

| 级 | 位置 | 内容 | 依赖规则 | 例子 |
| --- | --- | --- | --- | --- |
| **L0 技术工具** | `pkg/` | 与业务和平台无关的纯函数/小库 | **不依赖任何内部包**,可单独开源 | 错误类型、游标分页、ID 生成、金额与舍入、时间与自然日、脱敏、重试、校验器、手机号/证件号格式 |
| **L1 平台内核** | `kernel/` | 有状态的技术框架:装载、配置、事件、调度、状态机、策略、配额、审计、幂等、事务、迁移、可观测 | 只依赖 `pkg/`、`ports/` | 见 5.3 |
| **L2 共享业务域** | `shared/` | 业务通用、但不属于某个业务域的能力 | 只依赖 L0/L1;**不得依赖任何业务模块** | `dict`(字典/标签/主体类型)、`media`、`entityref` |
| **L3 业务模块** | `modules/` | 15 个业务模块(R0~R6) | 依赖阶梯(4.2) | identity … notice |

L3 内部再分:R0 基础域(identity、trust、ai)是「几乎所有人都用」的业务通用能力,地位接近 L2 但带有较强的领域规则,所以放在业务模块层。

### 5.2 共享业务域

**① `dict`:字典、标签、主体类型(PRD 6.4、8.2、8.6)**

- `taxonomy`:以 `code` 为键的选项集合,维度包括 行业/子行业、区域(省市县)、**行业性质**(概要九类)、合作需求/合作提供(同一套选项才能求交,PRD 9.1)、会议/活动领域等。**只停用不删除**;选项增减由运营自助,无需发版。
- **字段与选项分开**(PRD 6.4.1):选项在 `dict` 里自助维护;**字段本身**(表里多一行)由代码里的 schema 定义,走研发排期。**不做通用低代码表单引擎**——它是典型的伪需求,成本远高于一期收益。
- **主体类型配置**:类型编码(创建后不可改)、名称、图标、是否可发布内容、是否首页可见、排序、状态;**画像字段模板**=「某类型的入驻表单显示哪些字段、哪些必填、顺序」,字段取自代码中登记的字段池。
- **`TagSet`(通用标签值对象)**:`{industry[], region, nature[], need[], offer[], domain[]}`,全部存 `code`。所有可发布/可被检索的实体(名片、内容、圈子、猫立方、圈内需求)**嵌入同一个 `TagSet` 结构**,并通过 `dict.ValidateTagSet` 统一校验。这是概要所说「平台核心机制和难点」的落点:匹配、搜索、推荐、AI 抽取的输出都收敛到它。

**② `entityref`:实体引用**

- `EntityRef{type, id}`,`type` 取自注册表(`user`、`org`、`content.project`、`content.product`、`circle`、`cube`、`cube.project`…)。
- 各模块注册 `EntityResolver`:`Resolve(ref) → {title, cover, status, ownerRef, visibility}`。
- 使用方:收藏/关注(social)、举报(trust)、挂载(circle)、关联项目(cube)、审核任务(trust)、审计、搜索结果回填。**一套引用体系,没有「每个模块自己的 targetType 枚举」**。
- 与 PRD 同构:挂载「引用,不复制」(5.12.5)、圈内条目「来源可追溯」(5.12.7)。

**③ `media`:媒体**

- 统一上传(小程序直传预签名 URL)、类型与大小校验(PRD 8.9.2)、缩略图、CDN 域名、`Bind(ownerRef)` 记录引用,实体关闭/删除时回收孤儿文件。内容安全的图片检测由 trust 通过 `ReviewSubjectProvider` 取图,不由 media 调用。

**④ `Badge`(认证标识)统一机制**:`verify` 输出标识 `{code, label, level}`,如「实名」「企业认证」「组织已核验(红框)」「猫平方官方合作认证」(概要)。前端按 `code` 映射样式,**新增标识类型 = 加一条配置 + 一个样式,不改接口**。

### 5.3 平台内核提供的共享机制

| 机制 | 说明 | 谁用 |
| --- | --- | --- |
| `policy` 授权引擎 | 只放引擎与 `Actor` 装配:各模块注册 `CapabilityProvider`(能力)与 `PolicyRule`(规则);返回 `Decision{Allow, Reason}`。内核**不 import 任何业务模块** | 所有模块 |
| `quota` 限额引擎 | 模块注册 `QuotaDef{key, window(day/total), scope(user/circle/cube)}`;**数值来自配置**(PRD 0.3、11.5);计数落 `sys_quota_counter`(自然日窗口,Asia/Shanghai);超限返回 `Reason`。PRD 11.5 的 15 项数字规则,每项 = 一条 `QuotaDef` | circle(建圈、圈内发布、公告、挂载)、cube(成员数、可加入数)、membership(子账号) |
| `settings` 配置 | 模块注册 `SettingsSchema`(键、类型、范围、默认值、说明、是否敏感);后台**自动生成配置界面**;带版本、生效时间、操作人审计;scope 支持 platform/space | 价格、比例、限额、权重全部 |
| `statemachine` | 声明式 `{from, event, to, actor, guard}`;统一写状态日志并发布事件;**非法转移在引擎层拒绝** | 17 张状态流转表 |
| `scheduler` | 模块注册 `SchedulerJob`(到期转态、日结、对账);PG 咨询锁保证全局单活;批量、幂等、可重入 | 到期转态、通知合并、对账 |
| `eventbus` | Outbox + 订阅;幂等表;死信与重放 | 全体 |
| `idempotency` | `Idempotency-Key` 中间件与存储;支付回调、创建订单、发布内容共用 | trade、content、cube… |
| `scopedrepo` / `tx` | 仓储基类:强制注入 Scope、软状态过滤;事务管理器同事务写业务表 + outbox | 所有 `infra` |
| `sensitive` | `Visible[T]` 与加密、盲索引、日志脱敏 | identity、profile、verify |
| `audit` | 追加写审计;退款、封禁、改配置、查看联系方式、导出对账必记 | 全体 |
| `obs` | OpenTelemetry 埋点封装(trace/metric/log 同一入口,带 `module` 标签) | 全体 |

### 5.4 前端共享

后端的边界映射到前端:前端也按模块切(`features/<module>`),通用部分下沉到共享包。

| 共享包(`packages/`) | 内容 |
| --- | --- |
| `api-client` | 由 OpenAPI **自动生成**的 TS 客户端与类型(小程序、后台共用,不手写请求) |
| `domain-types` | 状态枚举、`Reason` 码、`EntityRef`、`TagSet`、`Badge` 等跨端类型(由契约生成,不手写) |
| `policy-hints` | 后端 `Decision.Reason` → 用户可读文案与「如何解锁」动作(开通会员、完成实名…),小程序与后台共用 |
| `taxonomy-kit` | 行业/区域/需求选择器的数据结构与搜索逻辑(组件层在各端) |
| `form-kit` | 校验规则(与后端同源,由契约导出)、字段模板渲染协议(按主体类型字段模板渲染入驻表单) |
| `utils` | 金额、时间(自然日)、脱敏展示、游标分页 hook |

**小程序专有共享组件**(`apps/miniapp/src/shared/`):`ContentCard` 卡片注册表(项目/产品/会议/活动/人/单位六类共用壳,按类型挂载字段区)、`PolicyGate`(受限能力自动灰显并展示 `Reason`)、`TaxonomyPicker`、`Uploader`、`CursorList`、`EmptyState`、`SubscribeAsk`(在上下文动作处请求订阅授权)、`PayButton`。

**后台专有共享组件**(`apps/admin-web/src/shared/`):`SettingsForm`(由 `SettingsSchema` 渲染)、`ReviewQueue`(统一审核队列)、`AuditTrail`、`StateTimeline`(状态日志)、`DataTable`(分页、筛选、导出)。

### 5.5 「放哪里」决策树

```text
要复用的这段代码/表/规则……
│
├─ 与业务无关(纯函数、格式、算法)?            → pkg/ (L0)
├─ 是技术框架,且有状态(配置/事件/调度/策略)?  → kernel/ (L1)
├─ 是外部能力(支付/短信/存储/LLM/审核接口)?   → ports/ 定义接口 + adapters/ 实现
├─ 业务通用,且至少 3 个业务模块都要?          → shared/ (L2),且不能依赖业务模块
│    └─ 只有 2 个模块用?                       → 放在较低阶的那个模块 contract 里,让高阶依赖
├─ 只服务于一个业务动作?                      → 留在该模块 internal/,不要提前抽象
└─ 多个模块要「读」同一个展示视图?             → bff/ 聚合,不下沉
```

**三次原则**:同一段业务逻辑出现第三次才抽取;抽取时必须同时给出复用方清单,并保证它放在使用方都能依赖的最低一层。

### 5.6 常见反模式(评审时直接打回)

| 反模式 | 为什么错 | 正确做法 |
| --- | --- | --- |
| 为了复用,把「用户昵称+头像」冗余字段复制到 10 张表 | 改一处漏九处 | 存 `user_id`;展示在 `bff` 聚合;确需冗余(如搜索文档)走事件投影 |
| `util`/`common` 大杂烩包 | 谁都能往里放,最终变成隐式依赖中心 | 只允许 `pkg/` 下的**单一职责小包**(如 `pkg/money`) |
| 低阶模块直接调高阶模块「通知一下」 | 破坏阶梯、产生环 | 发事件;或在低阶开注册表 |
| 把枚举写死在代码里 | 违反「规则即数据」 | 进 `dict` 或 `settings` |
| 每个模块自己做一遍分页/幂等/错误码 | 口径不一致 | `pkg/page`、`kernel/idempotency`、统一错误码段 |

**分层职责**(取代 v2.0 的 `transport → app → domain → infra` 描述,补上依赖方向):

| 层 | 可以依赖 | 禁止 | 备注 |
| --- | --- | --- | --- |
| `transport` | `app`、`pkg` | 直接调用 `infra`、其他模块 | 只做协议转换;不写业务判断 |
| `app` | `domain`、`infra` 接口、其他模块 `contract`、`kernel` | 写 SQL | 事务与事件在此;**跨模块调用只发生在这一层** |
| `domain` | `pkg`、本模块子域 | 任何 I/O、`kernel` 之外的框架 | 纯规则,可纯单元测试;策略函数(PRD 权限矩阵)在这里 |
| `infra` | `kernel/scopedrepo`、`ports` | 其他模块的表 | 仓储接口定义在 `domain`/`app`,实现在 `infra`(依赖倒置) |

**为什么用 `internal/` 而不是靠 lint**:Go 编译器规定,`modules/cube/internal/...` 只能被 `modules/cube/...` 子树内的代码 import。其他模块想 import 它,**编译不通过**。lint 只负责 `contract` 之间的阶梯方向与 SQL 前缀这类编译器管不到的规则。

**装配根**(`app/wire.go`)是唯一同时 import 所有模块与适配器的地方;模块自己不 import 适配器实现,只用 `ports` 接口。S0 → S1 → S2 的差别只在这里的配置,见第 11 章。

### 6.6 扩展清单(新增东西时照着做)

**新增一个业务模块**

1. 在阶梯表(4.2)定阶、写画布 `docs/modules/<m>.md`、登记表前缀与错误码段。
2. 建 `contract/`(Facade、事件、开口)与 `module.go`;`internal/` 四层。
3. 注册:`StateMachineDef`、`SettingsSchema`、`QuotaDef`、`PolicyRule`、`SchedulerJob`、`NoticeTemplate`、`AdminSection`(按需)。
4. 事件 Schema、OpenAPI 路径、迁移脚本、`CODEOWNERS`。
5. 前端 `features/<m>`(小程序/后台各一份,按需)。
6. 通过 `make lint`(archcheck)与权限矩阵、状态机测试。

**新增一种内容类型**(如「招聘」「展会」):在 `content` 里实现并注册一个 `ContentKind`(字段 schema、校验、卡片字段、审核文本提取、`SearchDoc` 映射)+ 一张类型子表 + 小程序 `ContentCard` 的一个字段区。**不改 discovery、trust、circle、cube**。

**新增一种主体类型**(第七、第八类):后台「主体类型」加一条配置、选字段模板;不发版(PRD 6.4.2)。

**新增一个限额/价格/比例**:在所属模块 `SettingsSchema` / `QuotaDef` 登记一条;后台自动出现配置项;代码里只引用键名。

**新增一个第三方供应商**(换短信、换 LLM、换内容安全):在 `ports` 里已有接口时,只写一个 `adapters/<vendor>` 并通过契约测试套件;改配置切换。

## 7. 数据、权限与安全

v2.0 第 5 章的结论全部保留,以下为 v2.5 的归位与补充。

### 7.1 可见性与隔离

- **Scope**:`platform / space / org / cube / circle / self`。所有仓储经 `ScopedRepo`,调用方必须传入 `Scope`,拿不到「裸查询」;`space` 在一期恒为主站(4.8)。
- **RLS 仅兜底**:只在泄漏代价最大的表启用(`cub_` 内项目/任务/报备/研究记录、`msg_` 消息与会话成员)。每个请求**在事务内** `SET LOCAL app.user_id = …`(连接池复用下不得用 `SET`);策略按表单一职责,不用 `OR` 叠加;平台管理员走独立数据库角色。
- **关闭 ≠ 删除**:实体统一 `status + closed_at`,仓储默认过滤已下架/已解散,后台查询需显式声明。

### 7.2 授权:能力 + 资源内角色 + 状态门

- 引擎在内核(5.3),**规则分散在各模块**:`identity` 提供「已实名」,`membership` 提供「会员生效中」,`verify` 提供「已认证/组织管理员」,`cube` 提供「猫立方内角色」,`trust` 提供「是否被限制发布」。`Actor` 由这些 `CapabilityProvider` **惰性装配**(请求内缓存),内核不依赖任何业务模块。
- 每个模块在自己的 `domain/policy.go` 写规则函数,返回 `Decision{Allow, Reason}`;`Reason` 同时驱动前端提示与 AI 入口灰显。
- **PRD 即测试**:3.2 权限矩阵每一格 = 一条表驱动用例(`tests/matrix/`),3.3 认证状态同理;改权限先改用例。

### 7.3 认证与会话

沿用 v2.0:Access Token 2 小时、RS256,**只含 `sub / sid / authz_ver`**;会员到期、被移出猫立方、封禁等事件递增 `authz_ver`,网关比对,**无陈旧窗口**;Refresh Token 7 天滚动轮换、哈希存储、可吊销;同账号最多 3 个活跃会话;微信 `session_key` 只在服务端短期使用,**不下发、不入日志**;登录失败锁定。

### 7.4 后台账号与 RBAC(新增)

PRD 只有「平台管理员」一个角色,但需求里存在不同职责(内容审核、认证审核、财务复核、渠道结算、配置维护)。建议固定五个内置角色,权限点由各模块 `AdminSection` 声明:

| 角色 | 典型权限 |
| --- | --- |
| 超级管理员 | 全部;后台账号管理、配置中心 |
| 运营 | 主体与内容管理、字典与选项、猫立方/圈子管理、公告 |
| 审核员 | 审核队列、举报复核、认证审核 |
| 财务 | 订单、退款发起、对账、结算复核与打款标记 |
| 渠道经理 | 运营商开户、佣金规则、保底任务跟踪 |

所有后台账号强制二次验证;**敏感操作(退款、封禁、改价格与比例、导出、结算)二次确认并写审计**;「复核」与「执行」不得同一人(结算单 PRD 11.1 #17 的「财务复核」落点)。角色带 `space_id`(4.8)。待产品确认(第 14 章)。

### 7.5 敏感数据

沿用 v2.0:手机号/证件号/联系方式 AES-256-GCM 字段加密 + `phone_hmac` 盲索引(独立密钥,支撑「是否已注册」唯一校验);信封加密与密钥轮换;对外 DTO 中敏感字段用 `Visible[T]` 包装,**漏写策略的结果是看不到,不是泄漏**;联系方式查看全量审计 + 按用户/日阈值告警与限频(防抓取);日志统一脱敏;**开放 API/Webhook 字段白名单不含联系方式**(PRD 10.4.3 #4)。

### 7.6 数据生命周期

| 数据 | 策略 |
| --- | --- |
| 聊天记录 | 留存 ≥ 6 个月(PRD 10.4.3);`msg_message` 按月分区,超期分区压缩归档到对象存储,保留可检索元数据 |
| 账号注销 | `identity` 发布 `identity.UserDeactivated` → 各模块订阅处理:手机号/证件号/头像匿名化,群聊与项目记录因他人协作保留,发送人显示「已注销用户」;**各模块自己负责自己的数据**,identity 不触碰他人表 |
| 已关闭/已结束实体 | 只读保留,不物理删除(PRD 11.1 总原则) |
| 审计 | 追加写,独立保留期(可配) |

> 待确认:聊天留存 6 个月 与 账号注销后他人可见聊天记录 的口径(法务,第 14 章)。

## 8. 关键业务机制

### 8.1 状态机与到期转态

PRD 11.1 的 17 张状态流转表,每张归**一个模块**拥有,以 `StateMachineDef` 声明(`{from,event,to,actor,guard}`),由内核引擎执行并写状态日志、发布事件。

| 模块 | 拥有的状态机(PRD 11.1 #) |
| --- | --- |
| verify | #1 实名、#3 认证申请、#4 身份核验 |
| content | #2 平台内容 |
| cube | #5 猫立方、#6 成员、#7 猫立方内项目、#8 任务、#9 报备、#13 猫立方订阅 |
| circle | #10 圈子、#11 圈内需求 |
| membership | #12 会员 |
| trade | #14 分摊订单、#15 订单 |
| channel | #16 运营商、#17 佣金结算单 |

**到期转态**不为每个实体建延时任务:业务表带 `expires_at`(部分索引),各模块注册 `SchedulerJob`,`scheduler` 角色每分钟批量扫描、分批、幂等执行(会员/订阅/临时圈/圈内需求/分摊截止/订单超时/邀请链接/企业版 30 天回落)。**自动动作只做「到期转态」,不做「自动通过」**(PRD 11.1 总原则)。

### 8.2 猫立方项目与平台项目(落实 PRD 8.7 硬约束)

PRD 要求:猫立方内「项目」与平台「项目」**数据打通**,但**状态相互独立**;一个项目可同时进入多个猫立方。设计为**引用 + 本地状态**:

```text
cnt_item (kind=project)          平台项目:审核中 / 展示中 / 已下架    ← content 拥有
        ▲
        │ content_project_id(可空,仅存 ID,无外键)
cub_project                      猫立方内项目:类型(研究/承接)、负责人、进行中/已关闭 ← cube 拥有
   ├── cub_task        任务(project_id 可空 = 「内部工作安排」)
   ├── cub_report      重点客户报备
   ├── cub_research    研究记录(决策结论)
   └── msg session     项目群聊(1 项目 1 群聊,经 SessionMemberResolver)
cub_project_link_req             引入他组织项目的确认申请:待确认/已同意/已拒绝
```

- 同一平台项目进入 A、B 两个猫立方 = 两行 `cub_project`,各自状态独立;**A 关闭不影响平台展示,也不影响 B**(PRD 5.6.8)。
- 猫立方内新建、尚未发布的项目 `content_project_id` 为空;「发布到平台」调用 `content.Publish`,回写 ID。
- 平台项目被下架:`cub_project` 保留,卡片通过 `EntityResolver` 读到状态后显示「平台已下架」,不删除。
- 引入规则:本组织项目猫王/猫蜜直接加入;他组织项目需项目方(或其猫王/猫蜜)确认;普通成员发起需猫蜜确认(PRD 5.6.8 #3~#5)——落在 `cub_project_link_req`。
- 圈内「到猫立方里办」:circle 调用 `cube.CreateProjectFromRef(sourceRef, title, body)`,**只带标题、正文、来源引用**;来源圈条目与猫立方项目状态独立(PRD 5.12.7)。

### 8.3 内容类型:`ContentKind` 插件(落实 PRD 2.3「四类表单字段各自独立」)

```text
cnt_item            信封表:id、kind、owner_ref、title、cover、tagset(JSONB)、status、
                    published_at、space_id、visibility、version …… (四类共有)
cnt_project         项目子表:金额、阶段、核心优势(会员可见)、联系人 …… (项目独有字段,类型化列)
cnt_product         产品子表(+ 产品库入库字段)
cnt_meeting         会议子表:会议时间、地点 ……
cnt_event           活动子表:活动领域标签 ……
```

- 每种 `ContentKind` 实现:字段 schema 与校验、卡片字段(PRD 5.2.3)、详情字段、「会员可见」字段清单、审核文本/图片提取、`SearchDoc` 映射、状态机共用。
- **共有与独有分开**:能筛选、排序的用类型化列,仅展示用的少量扩展字段才用 JSONB。**不要把四类做成一张大宽表,也不要做成纯 JSON**。
- 新增内容类型 = 一个 Kind + 一张子表(6.6),不改 discovery/trust/circle/cube。
- 产品库(PRD 6.3「产品入库三步流程」)属于 content 的后台流程,「入库审核」走 trust 的统一审核任务;**不设「产品总库」**(PRD 2.2 D1)。

### 8.4 支付、分摊与佣金

**口径与 v2.0 一致**(以 PRD 8.3.1、10.4.3 为准,微信支付与法务待确认):会员年费与猫立方订阅费是平台自身经营收入;分摊是「同一张订阅订单的多笔认筹付款」,钱进平台商户号、平台统一开通订阅,**不向第三方分账**;运营商佣金是平台月结支出,不设资金池;**禁止个人对个人、二级清算与多级分销**。

**v2.5 的模块职责切分**(v2.0 把这些都放在 `trade`):

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `trade` (R1) | 订单、支付(回调验签、幂等)、退款、每日对账、分摊认筹与成团、`OrderFulfiller` 开口 | 价格怎么算、买的是什么、权益怎么给 |
| `membership` (R3) | 会员价格计算(年费 × 年限 × 折扣系数,**只维护一个价格锚点**)、下单、履约(开通/续期)、退款金额计算(剩余完整年数 × 年费 × **实付折扣系数**,系数在订单价格快照里) | 收钱 |
| `cube` (R3) | 订阅档位价格、下单、履约(升降档)、分摊的发起与档位校验 | 收钱 |
| `channel` (R4) | 订阅 `OrderPaid`,按配置比例(初始 30%/10%)生成佣金流水并写入比例快照;月结单状态机;保底任务进度;保证金台账(预收款,不与收入混记) | 收钱 |

- **订单模型**:`trd_order(biz_type, biz_ref, amount, price_snapshot, status)`;`trd_payment`(一单多笔,`out_trade_no` 唯一);`trd_apportion_group(N, deadline, status)`;`trd_pledge`;`trd_refund`(幂等键 = 支付单号 + 原因)。
- **成团原子性**:认筹支付成功后,在**同一个 `trade` 事务**内锁定 `apportion_group` 行并计数,达到 N 即置「已成团」并将订单置「已支付」。这一步**不跨模块**,因此可强一致。
- **开通订阅**:订单已支付 → `OrderPaid` → `cube` 的 `OrderFulfiller` 履约(幂等,以订单 ID 去重)。这一步是最终一致(秒级);履约失败自动重试,超过阈值告警,后台可手动补偿——**不让「付了钱没开通」成为沉默失败**。
- **未成团**:到期扫描 → 对全部已付认筹逐笔幂等退款,全部完成才终结。
- **红线写进结构**:运营商只有 `referrer_operator_id` 单列,**没有上级字段、不能自建下级**,从 schema 上杜绝多级分销(PRD 7.3、10.4.3)。
- 用户端不提供退款入口;退款只由后台「财务」发起(PRD 8.3.1)。

### 8.5 搜索与匹配(`discovery`)

**数据来源:事件投影,不读他人表。**

```text
profile / content / circle / verify / membership / social
        │  发布带 SearchDoc / MatchProfile 的事件(shared 中的统一 DTO)
        ▼
discovery 订阅 → dsc_search_doc(统一搜索文档:人/单位/项目/产品/活动/会议/圈)
              → dsc_match_candidates(每个用户的 Top-K 候选,预计算)
```

- `SearchDoc` 携带:标题、摘要、`TagSet`、区域、认证标识、会员等级、状态;**不携带手机号等敏感字段**。下架/关闭类事件同步删除或置灰,**文档可随时由事件回放重建**。
- **搜索**:一期 PostgreSQL(`pg_trgm` / 中文分词扩展视云 RDS 而定),通过 `Search` 端口抽象;量大再换 Meilisearch/ES,索引仍由同一批事件驱动。
- **匹配**:① 「先给后要」:注册后立刻按粗标签给 3 条结果;② 画像更新事件触发候选重算(区域/行业/标签倒排求交),Top-K 写入 `match_candidates`,首页只读预计算结果以保证首屏 ≤ 3 秒;③ 评分公式权重配置化(需求供给互补 40%、行业 25%、区域 20%、身份互补 15%,后台可调并保留版本);④ **同分按会员等级(企业版 > VIP > 普通),不设推荐位或插队**(PRD 8.3.1);⑤ 推荐理由用规则模板生成,不依赖 LLM;⑥ 二期用 pgvector 向量相似度作为可开关的第五维。
- 一期主场景是「找对人 + 联系上」(PRD 1.4.1),**不依赖算法**:标签筛选与关键词检索必须独立可用,匹配只是增强。

### 8.6 消息与通知

**`msg`(R1,会话与消息)**——沿用 v2.0 的增量同步设计:客户端带 `cursor` 拉取,前台 3 秒轮询、无新消息指数退避;**未读数 = 会话最大序号 − 已读游标**(PG,幂等,免 Redis 计数器);单聊会话 `(min(uid),max(uid))` 唯一,与消息列表同一套会话(PRD A9);群聊成员由 `SessionMemberResolver` 决定(cube 注册),**msg 不认识猫立方**;二期 WebSocket 只作为「加速通道」,仍走同一套同步接口,`Realtime` 适配器默认空实现。

**`notice`(R6,通知中心)**——把 PRD 11.3「消息通知触达总表」做成**数据驱动**:

- 各模块在自己的 `NoticeTemplate` 里声明「事件 → 接收人规则 → 文案 → 渠道(站内/订阅消息)→ 是否合并」;`notice` 订阅全部业务事件并执行。业务模块**从不直接发通知**。
- **订阅消息授权额度**:`ntc_subscribe_quota(user, template, remaining)`;在「关注/加入猫立方/提交任务」等上下文动作处申请授权,发送时消耗;无额度降级为站内未读,并在下次进入小程序时提示开启。
- **圈内通知合并**:同圈同自然日一条并累计条数,用 `ntc_digest(circle_id, date, count)` upsert 计数 + 日结任务发送,避免「先判断再自增」竞态。
- 订阅消息模板需**提前申请**(类目审核有周期),列入立项当天启动项。

### 8.7 内容安全与审核(`trust`)

```text
用户提交 → 敏感词前置过滤(本地,后台可维护)
        → 文本:同步机器检测,命中拦截并记违规
        → 图片/音视频:异步检测;回调前「审核中」(图片占位),通过 → 展示中,命中 → 自动下架
        → 展示中 → 用户举报 → 人工复核(24 小时内)→ 属实:下架 + 记分(3 次限制发布 7 天)→ 严重者封号
```

- **谁都不调微信内容安全接口**,统一经 `Moderation` 端口(接口版本、参数以微信官方最新文档为准)。
- **审核对象不写死**:`content`、`msg`、`circle`、`profile`、`verify` 各自向 `trust` 注册 `ReviewSubjectProvider`(怎么取文字/图片、结论怎么落回)。**新增一种需要审核的对象,不改 trust**。
- 统一审核任务表 `trs_review_task`:来源包括机器命中、用户举报、认证材料、产品入库、高风险类目抽检(金融/医疗/政府项目);后台一个队列,按 SLA 排序。
- AI 辅助审核只做预分类与摘要,**处罚必须人工确认**。引流词(「加我微信/私下联系」,PRD 9.3)命中先提示再记分,词库后台可维护。

## 9. AI 能力层

v2.0 第 7 章的原则与场景矩阵保留:**可选可降级、人在回路、隐私最小化、不新增页面、可评估可控成本、模型可替换**;十类场景与阶段不变(一期:一句话入驻、发布智能草稿、自然语言搜索、智能客服、审核辅助;二期:推荐理由与破冰语、语义匹配、猫立方协作、圈内需求整理;三期:运营洞察)。

**v2.5 的落位**:

| 项 | 做法 |
| --- | --- |
| 模块位置 | `ai`(R0),**所有业务模块可依赖,不依赖任何业务模块**;未装载时注入 `Noop` 实现,调用方拿到「不可用」即走原有手动路径 |

| 入口位置 | 小程序 `ai-entry` 组件嵌入入驻页/发布页/搜索页;`ai` 不可用时组件自动隐藏 |
| 隐私 | 手机号、证件号、联系方式不进提示词与向量;调用审计 |
| 范围提示 | 一期场景属于「替代填表的辅助入口」,仍是需求范围变化,**建议产品确认后纳入**;不纳入时 `ai` 不装载,其余设计不受影响 |

### 10.1 API 组织

| 入口 | 路径 | 用途 | 特点 |

### 10.2 小程序体验

1. **聚合接口放 bff**,单次返回卡片流 + 画像进度 + 未读数;不让小程序为首屏发多次请求。
2. **主包体积预算**:仅 Tab 壳 + 事业线 + 消息;其余分包按需加载(6.3)。
3. **受限能力一律用 `PolicyGate`**,不在页面里重复写「是不是会员」的判断。

## 11. 部署、可靠性与运维

### 11.1 角色、模块、适配器三个开关

```text
catcube serve --roles=api,worker,scheduler,admin \
              --modules=identity,dict,media,trust,profile,... \
              # adapters 来自配置:queue=pg|nats|rabbit  cache=local|redis  search=pg|meili|es
```

- **角色**:`api`(对外 HTTP)、`worker`(事件与任务)、`scheduler`(到期转态,PG 咨询锁全局单活)、`admin`(后台路由)。
- **模块**:`modules.enabled` 开关;启动时按 `DependsOn` 与 4.2 阶梯做拓扑与缺失检查(缺依赖直接启动失败,而不是运行时报错)。
- **适配器**:业务代码只依赖 `ports`;**S0→S1→S2 只改配置与 `wire.go`,不改业务代码**。

### 11.2 三档部署形态

| 档位 | 阶段 | 形态 | 新增依赖 |
| --- | --- | --- | --- |
| S0 一体 | 内测/一期启动 | 1 台云主机:app(全角色全模块)+ PostgreSQL;PITR 备份 | 无 |
| S1 分角色 | 一期正式运营(目标可用性 ≥ 99.5%) | api × 2 + worker × 1(含 scheduler)+ 托管 PG 主从 + Redis | Redis |
| S2 分布式 | 规模增长/二期 | K8s;`msg`、`ai`、`trade`、`discovery` 按 4.7 判据独立部署;事件总线升级为 NATS/RabbitMQ;搜索切 Meili/ES | MQ、搜索 |

一期容量(PRD 10.4.1:万级注册、日活千级、峰值并发百级、内容万级、圈子千级、猫立方百级)用 S0~S1 即可满足。

### 11.3 高可用与降级

| 项 | 方案 |
| --- | --- |
| 备份 | WAL 归档 + 每日全备;建议 RPO ≤ 5 分钟、RTO ≤ 1 小时(需研发与业务确认);每季度恢复演练 |
| 降级矩阵 | AI 不可用 → 原表单;搜索适配器故障 → 回退 PG 简单检索;内容安全接口超时 → 文本发布进「审核中」队列重试,**不放行**;Redis 不可用 → 回退进程内缓存/限流;`notice` 故障 → 业务不受影响,事件积压后重放 |
| 健康检查与停机 | `/healthz`(存活)、`/readyz`(依赖就绪);停机先摘流量再排空任务 |
| 事件积压 | Outbox 与任务表监控积压与最老消息年龄,超阈值告警;死信可在后台重放 |

### 11.4 配置三层

沿用 v2.0 的**启动配置 / 业务配置(`settings` 表,带类型校验、版本、生效时间、审计)/ 特性开关**三层,v2.5 补充:业务配置由各模块声明 `SettingsSchema`,后台**自动生成界面**;支持 `scope`(platform / space)覆盖(4.8)。

### 11.5 发布与可观测

- **迁移**:expand → migrate → contract,向前兼容、可回滚,独立角色执行。
- **灰度**:特性开关按用户/比例/白名单放量;小程序走体验版 → 审核 → 全量,配合开关实现服务端灰度。
- **可观测**:OpenTelemetry 一套埋点,日志结构化并带 `request_id / module / user_id(脱敏)`;**每个模块的指标带 `module` 标签**,便于判断哪个模块该拆。看板:注册、画像完成度、匹配点击、联系发起、会员转化、支付成功率、猫立方开通、审核积压。告警(初始值可配):P99 > 3s、错误率 > 1%、支付回调失败 > 0、**履约重试超阈**、审核 SLA 将超时、AI 采纳率骤降或成本异常。
- **产品埋点**:小程序统一埋点规范(事件名与属性由契约登记),一期只采集漏斗必需项(注册 → 画像 → 搜索/匹配点击 → 联系发起 → 开通会员),避免「数据资产叙事」式的过度采集(PRD 1.2.3)。

| 模块独立启动 | 只装载某模块及其依赖能启动并通过自身测试(证明可拆) | CI 矩阵 |
| AI 评测 | 固定样本集:抽取准确率、`TagSet` 合法率、降级路径;提示词变更必须过评测 | `ai` |
| 压测 | PRD 10.4.1 目标 + 5~10 倍余量;联系方式抓取压测 | `tests/perf` |
| 安全 | 依赖漏洞、SAST、越权测试、渗透、支付回放 | 上线前 |

## 13. 实施路线

**按依赖阶梯自底向上,阶梯内并行**。注意与 v2.0 的一处调整:PRD 1.4.1 把「联系上」定为 VIP 的第一权益,是**唯一能立刻验证付费意愿的动作**,所以会员支付必须进入主链路阶段,而不是推到猫立方之后。

| 阶段 | 内容 | 退出标准 |
| --- | --- | --- |
| 0 立项准备 | 订阅消息模板申请、ICP 备案、内容安全接入、支付合规确认、AI 合规评估、字典种子初稿;**确认第 14 章待确认项** | 外部事项均有负责人与时间表 |
| 1 地基 | monorepo 与 CI(`archcheck`、契约生成)、`pkg`、`kernel`、`ports/adapters`(pg、local、wechat、oss)、**R0**(identity、trust 骨架)、`dict`、`media`;权限矩阵与状态机测试框架 | S0 一键起;空模块能按阶梯装载;边界检查在 CI 生效 |
| 2 主链路 | `profile`、`verify`(实名)、`content`、`social`、`discovery`(规则版 + 先给后要)、`trust`(内容安全/举报)、`trade` + `membership`(会员支付、联系方式可见)、`msg`(异步单聊) | 「找对人 + 联系上 + 付费开通」闭环跑通(PRD 1.4.1) |
| 3 协作 | `cube`(空间/成员/项目/任务/报备/订阅/分摊)、`circle`、`notice` | 支付幂等与并发成团测试通过;状态机测试通过 |
| 4 渠道与后台 | `channel`、后台全功能与 RBAC、对账与结算闭环、认证全类型 | 对账结算闭环 |
| 5 AI 一期场景 | 一句话入驻、发布草稿、自然语言搜索、智能客服(经产品确认) | 关闭开关时全链路无影响;采纳率与成本可观测 |
| 6 联调上线 | 越权/渗透/压测、S1 环境、灰度放量 | 达到 PRD 11.4 验收标准 |

**分工方式**:按**模块 owner** 而非按技术层分工。建议三条并行泳道——(A)身份与内容:identity、profile、verify、content、dict、media;(B)交易与协作:trade、membership、cube、circle、channel;(C)触达与发现:msg、notice、discovery、trust、ai。小程序与后台前端按同样的 `features/` 对应认领模块。
