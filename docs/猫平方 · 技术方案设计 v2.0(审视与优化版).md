# 猫平方商业一体化综合服务平台 · 技术方案设计 v2.0

版本:v2.0(在 DeepSeek 方案 v1.0 基础上审视优化) | 依据:《产品需求说明书 v2.5》 | 编制日期:2026-10-08 | 适用对象:研发 / 架构 / 项目管理

## 0. 结论先行

**对 v1.0 的总体评价**:覆盖面完整,安全与合规意识较好(RLS、字段加密、支付红线、内容安全、订阅消息模板),这些保留。但存在三类问题:

1. **过度设计**:12 个微服务 + Consul + Nacos + Kong + RabbitMQ + ES + 独立向量库 + ELK + Jaeger + Argo Rollouts。需求文档 10.4.1 给出的一期量级是「万级注册、日活千级、峰值并发百级、猫立方百级」,而 0.1 的编制原则是「尽量从简」。这套栈的运维成本远高于业务价值,小团队跑不动。
2. **与 PRD 冲突或遗漏**:支付口径自相矛盾、权限模型代码有错、多项 PRD 硬性规则(到期转态、后台可配、账号注销、聊天留存、佣金红线)没有落地设计。
3. **AI 只是二期外挂**:没有回答「如何减少用户的复杂操作」,而 PRD 9.1 恰恰把「填表门槛」列为首要矛盾。

**v2.0 的核心思路**:一个「**平台内核 + 可装载业务模块 + 可替换能力适配器**」的**模块化单体**,同一份代码、同一个二进制,通过配置从**单机一体**平滑演进到**多角色分离**,再到**按模块拆分的分布式**。AI 作为**可降级的能力层**嵌入入驻、发布、搜索、猫立方协作等高频填写场景,**有 AI 更省事,没有 AI 也能完整使用**。

| 你的要求 | v2.0 的设计手段 |
| --- | --- |
| 1 先进、创新、结合 AI | AI 网关 + 十类场景矩阵(第 7 章);pgvector 语义匹配;事件驱动 + Outbox;OpenTelemetry 统一可观测 |
| 2 交互好、少操作、不强依赖 AI | 「说一句话自动填画像/发布草稿」;自然语言搜索;每个 AI 功能必有手动路径与降级开关 |
| 3 精炼、单体到分布式按需扩展 | 必选依赖仅 PostgreSQL;Redis、搜索引擎、MQ 全部为可选适配器;三档部署形态(4.4) |
| 4 开放、安全、按需装载、灵活组装、易用、易运维、可扩展、高可用 | 模块清单 + 装载机制(4.3);开放 API/Webhook(8.3);三层配置(9.4);备份与高可用方案(第 9 章) |

## 2. 设计原则

1. **先单体,后拆分**:模块边界一开始就按「可拆」来划,但部署上先合一。拆分是运维动作,不是重写。
2. **依赖做减法**:必选依赖只有 PostgreSQL 和对象存储。其余(Redis、搜索、消息队列、向量库)都以「端口 + 适配器」接入,默认用 PostgreSQL 自带能力实现。
3. **规则即数据**:价格、比例、限额、权重、选项、主体类型全部进配置表(PRD 0.3),不进代码、不依赖发版。
4. **状态机显式化**:PRD 11.1 的 17 张状态流转表,代码里就是 17 个声明式状态机,非法流转在底层被拒绝。
5. **AI 可选、可降级、人在回路**:AI 只产出「草稿 / 建议」,用户确认才落库;任何 AI 故障不影响主链路。
6. **安全默认开启**:敏感字段默认不输出,需要策略显式放行,而不是需要开发者记得去过滤。

### 3.1 四层结构

### 3.2 技术选型(精炼版)

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 语言与框架 | Go 1.22+、Gin(沿用) | 单二进制、低内存,适合小团队运维;数据访问二选一并全项目统一:pgx + sqlc(类型安全、可控)或 GORM(上手快) |
| 主库 | PostgreSQL 16 + pgvector | 业务数据、消息、检索、向量、任务队列、配置全部可落在同一库 |
| 缓存 | 进程内缓存 → Redis | 单机用进程内缓存;多实例需要共享缓存/限流/分布式锁时启用 Redis |
| 异步 | Outbox + PG 任务表(`FOR UPDATE SKIP LOCKED`) → NATS JetStream / RabbitMQ | 默认零新增依赖;吞吐或解耦需要时换适配器 |
| 搜索 | PostgreSQL(pg\_trgm / 中文分词扩展,视云 RDS 是否支持) → Meilisearch / ES | 数据量万级,不需要一期上 ES |
| 网关 | 应用内中间件 → 云厂商网关 / Ingress | 不自建 Kong/APISIX |
| 配置与发现 | 配置文件 + DB 配置表;K8s 原生 Service | 不引入 Consul / Nacos |
| 部署 | Docker Compose → K8s | 同一镜像,不同启动参数 |
| 可观测 | OpenTelemetry + Prometheus + Grafana;日志输出 stdout 接云日志服务 | ELK、Jaeger 视规模再引入 |
| 小程序 | 原生或 Taro(二选一);TypeScript API 客户端由 OpenAPI 生成 | 接口契约单一事实源 |
| 后台 Web | React + Ant Design | 沿用 |
| AI | LLM / Embedding / OCR / ASR 外部服务,经 `ai` 模块统一接入 | 可替换、可关闭 |

**依赖三档**:必选 = PostgreSQL、对象存储;可选 = Redis、搜索引擎、消息队列、独立向量库、日志/链路后端;明确不引入 = Consul、Nacos、Kong/APISIX 自建、Argo Rollouts(灰度改用特性开关)。

### 4.1 模块清单(12 服务 → 10 模块)

运营后台(admin)不是独立业务,只是对上述模块 Facade 的聚合 BFF,同一二进制以 `admin` 角色路由暴露。

### 4.2 模块契约

- 每个模块对外只暴露 **Facade 接口**(Go interface)和**领域事件**,内部表对其他模块不可见;跨模块禁止 JOIN,需要的数据通过 Facade 查询或订阅事件冗余。
- 事件经 **Outbox**:业务事务内写 `outbox` 表,后台投递器读取并发布,保证「改数据」与「发事件」同事务、至少一次投递,订阅方按事件 ID 幂等。
- 典型事件:`ContentPublished`、`ProfileUpdated`、`OrderPaid`、`MemberExpired`、`CubeProjectClosed`、`ReportConfirmed`、`ModerationRejected`。
- 边界由 CI 强制:用 depguard / go-arch-lint 禁止 `module/a` 引用 `module/b` 的内部包,违反即构建失败。这样「以后拆」才不会变成「重写」。

### 4.3 按需装载与灵活组装

```go
// 每个模块实现统一接口,由内核按配置装载
type Module interface {
    Name() string
    DependsOn() []string          // 声明依赖,内核做拓扑排序与缺失检查
    Migrate(ctx context.Context, m Migrator) error
    Register(k *Kernel)           // 注册路由、事件订阅、定时任务、健康检查
}

// 启动:同一二进制,按角色与模块装载
//   catcube serve --roles=api,worker,scheduler --modules=identity,profile,content,...
// modules.enabled 与 features.* 来自配置;未装载模块的路由不注册、任务不调度
```

- **角色**:`api`(对外 HTTP)、`worker`(消费事件与任务)、`scheduler`(到期转态与定时任务,通过 PG 咨询锁保证全局单活)、`admin`(后台路由)。
- **模块**:用 `modules.enabled` 开关。比如先不装 `ai`、`match` 用规则版;运营商模块可只在有渠道的环境装载。
- **能力适配器**:用 `adapters.queue=pg|nats|rabbit`、`adapters.cache=local|redis`、`adapters.search=pg|meili|es` 切换,业务代码只依赖端口接口。

### 4.4 三档部署形态(同一份代码)

| 档位 | 适用阶段 | 形态 | 新增依赖 | 说明 |
| --- | --- | --- | --- | --- |
| S0 一体 | 一期启动 / 内测 | 1 台云主机(或 2 个容器):app(全角色全模块)+ PostgreSQL | 无 | 满足万级用户、百级并发;PG 做 PITR 备份,可用性靠快速恢复 |
| S1 分角色 | 一期正式运营(目标可用性 ≥99.5%) | api × 2 + worker × 1(含 scheduler)+ PG 主从(托管 RDS 优先)+ Redis | Redis | 滚动发布不中断;共享缓存与限流 |
| S2 分布式 | 规模增长 / 二期 | K8s;`msg`、`ai`、`trade` 按需独立部署,事件总线升级为 NATS/RabbitMQ,搜索切 Meilisearch/ES | MQ、搜索 | Facade 由进程内调用换成 gRPC 客户端适配器,业务代码不变 |

**升级路径只改配置与适配器,不改业务代码。** 当前一期容量预期(10.4.1)用 S0\~S1 即可满足,不需要一步到位。

## 5. 数据、权限与安全

### 5.1 数据可见性与隔离

PRD 里的隔离需求本质是**成员可见性**(猫立方成员、圈子成员、组织管理员),不是 SaaS 式多租户。设计如下:

- **可见性域(Scope)**:`platform` / `org` / `cube` / `circle` / `self` 五类。所有仓储方法必须经过 `ScopedRepo`,由它强制注入过滤条件,业务代码拿不到「裸查询」。
- **RLS 兜底**:只在泄漏代价最大的表启用(猫立方内项目/任务/报备/研究记录、消息、会话成员),作为第二道防线。
- **正确使用 RLS**:每个请求在**事务内**执行 `SET LOCAL app.user_id = ...`(连接池复用下不得用 `SET`);策略按表单一职责,不用 `OR` 叠加范围;平台管理员走独立数据库角色。
- **关闭 ≠ 删除**:所有实体用 `status` + `closed_at`,不做物理删除;仓储层默认过滤已下架/已解散,后台查询显式声明。

### 5.2 授权模型:能力 + 资源内角色 + 状态门

PRD 3.2/3.3 的权限由三个维度决定,合起来用代码化策略表达,不需要 Casbin:

| 维度 | 例子 | 来源 |
| --- | --- | --- |
| 账号能力 | 已实名、会员生效中、企业版、已认证 | identity 模块实时读取 |
| 资源内角色 | 猫王/猫蜜/成员、圈主、组织管理员 | 对应资源的成员表 |
| 资源状态 | 猫立方正常/封禁/解散、圈子已结束、内容已下架 | 资源本身 |

```go
// 策略即函数,可单元测试;每条规则对应 PRD 一行
func (p *Policy) Can(ctx context.Context, a Actor, act Action, r Resource) Decision {
    switch act {
    case ContactView:      // PRD 3.2:仅会员可见手机号/联系方式
        return need(a.MemberActive())
    case CubeManage:       // 仅猫王/猫蜜,且猫立方状态正常
        return need(r.Cube.Normal() && a.RoleIn(r.Cube, Owner, Assistant))
    case CircleCreate:     // 已实名 + 在建圈额度内
        return need(a.RealNameVerified() && p.quota.Check(a, "circle.owned"))
    }
    return Deny("unknown_action")
}
```

- **PRD 即测试**:3.2 权限矩阵每一格 = 一条表驱动用例,3.3 认证状态同理;权限改动时先改用例。
- 返回 `Decision{Allow, Reason}`,Reason 直接映射到前端提示(例如「开通会员后可查看」),同时驱动 AI 入口的灰显。

### 5.3 认证与会话

| 项 | 设计 |
| --- | --- |
| 登录 | 微信授权 + 手机号;备选短信验证码,登录失败锁定(PRD 5.1.1) |
| Access Token | 2 小时,RS256;**只含** `sub`、`sid`(会话 ID)、`authz_ver`(权限版本号),不含会员/角色 |
| 权限实时性 | 会员到期、被移出猫立方、封禁等事件递增用户 `authz_ver`;网关比对缓存中的版本号,不一致则强制刷新,**无陈旧窗口** |
| Refresh Token | 7 天,滚动轮换,PG 存哈希(Redis 可选加速),支持吊销 |
| 多端 | 同账号最多 3 个活跃会话,超出踢最早 |
| 后台 | 独立登录域与 Cookie,平台管理员强制二次验证;敏感操作(退款、封禁、改配置)二次确认并记审计 |

### 5.4 敏感数据保护

- **字段加密 + 盲索引**:手机号、身份证号、联系方式用 AES-256-GCM 加密,同时存 `phone_hmac`(HMAC-SHA256,独立密钥)用于「是否已注册」唯一校验与检索(PRD 5.1.3)。加密在仓储层显式调用,不依赖会被误判的内存标志位。
- **密钥管理**:信封加密(KMS 管理主密钥,数据密钥按库/按年轮换),密钥与数据分库存放。
- **默认不输出**:对外 DTO 中敏感字段由 `Visible[T]` 包装,只有策略放行才序列化;漏写策略时结果是「看不到」,不是「泄漏」。
- **联系方式查看审计**:会员「无限查看」(PRD 8.3.1)不等于无限制抓取。记录每次查看,按用户/日做异常阈值告警与限流,防止批量爬取。
- **日志脱敏**:统一日志中间件对手机号、证件号、令牌做掩码。
- **平台不得向第三方提供手机号**(PRD 10.4.3):开放 API 与 Webhook 的字段白名单中不含联系方式。

### 5.5 数据生命周期

| 数据 | 策略 |
| --- | --- |
| 聊天记录 | 保留 ≥ 6 个月(PRD 10.4.3)。消息表按月分区;热数据留库,超期分区压缩归档至对象存储,保留可检索的元数据 |
| 账号注销 | 提供注销入口:手机号/证件号/头像等个人标识匿名化;群聊与项目记录因他人协作需要保留,发送人显示为「已注销用户」 |
| 已关闭/已结束实体 | 只读保留,不物理删除(PRD 11.1 总原则) |
| 审计日志 | 独立表,追加写,保留期按合规要求配置 |

> 待确认:「聊天留存 6 个月」与「账号注销后数据删除」同时存在时,注销后他人可见聊天记录的处理口径,需法务确认(见第 12 章)。

## 6. 关键业务机制的技术设计

### 6.1 状态机与到期转态

- PRD 11.1 的 17 张状态流转表在代码中是 17 个**声明式状态机**:`{from, event, to, actor, guard}`。转移由统一引擎执行,非法转移直接拒绝;每次转移写状态日志并发布领域事件。
- **到期转态**不用每实体一个延时任务。统一在业务表放 `expires_at`(带部分索引),`scheduler` 角色每分钟批量扫描、分批处理、幂等执行:

| 实体 | 到期动作 |
| --- | --- |
| 会员 / 猫立方订阅 | 生效中 → 已过期;企业版到期同步回落全部子账号,子账号归属保留 30 天 |
| 临时圈 | 进行中 → 已结束(只读,不可续期) |
| 圈内需求 | 有效 → 已过期(默认 30 天,可续期) |
| 分摊订单 | 截止日未达标 → 未成团,触发全额原路退款 |
| 订单 | 待支付超时 → 已关闭 |
| 邀请链接 | 猫立方 7 天;圈子随圈子存续期 |

- 遵循 PRD 总原则:**自动动作只做「到期转态」,不做「自动通过」**;任务逾期不自动完成。

### 6.2 支付、分摊与佣金(重点)

**资金流梳理**(以 PRD 8.3.1、10.4.3 为准):

- 会员年费、猫立方订阅费都是**平台自身经营收入**,用户付款进入平台商户号,合规。
- **分摊本质是「同一张订阅订单的多笔认筹付款」**:成员付给平台的钱,是用来购买**平台自己的订阅服务**,并没有向猫王或第三方转付,因此不涉及向他人分账,也就不构成资金二次清算。v1.0 的「持牌机构监管专户 + 分账」方案在这个场景下既没必要,也与 PRD 口径冲突,予以删除。
- 分账能力仅在未来出现「向第三方结算」时再评估;运营商佣金是**平台月结支出**,走财务复核后打款,不是代收转付、不设资金池。
- 以上口径需**微信支付与法务确认**(商户类型、虚拟服务收款类目、开票),列入第 12 章待确认项。

**订单与支付模型**:

| 对象 | 设计要点 |
| --- | --- |
| `orders` | `biz_type`(member / cube\_sub)、`status`(待支付→已支付/已关闭)、价格快照:年费、折扣系数、年限、实付金额 |
| `payments` | 一单可有多笔(分摊场景);`out_trade_no` 唯一;回调验签 + 幂等落库 |
| `apportion_groups` | N(2 ≤ N ≤ 档位人数上限,含猫王)、`deadline`、`status`(进行中→已成团/未成团) |
| `pledges` | 认筹记录:成员、金额、支付状态 |
| `refunds` | 原路退款,幂等键 = 支付单号 + 退款原因;3–7 个工作日到账 |

- **成团原子性**:每笔认筹支付成功后,在事务内对 `apportion_groups` 行加锁,计数达到 N 即同一事务内置为已成团并开通订阅,杜绝并发超卖或漏开。
- **未成团**:到期扫描后对所有已付认筹创建退款单,逐笔幂等退款;全部退完才终结。
- **退款金额**:平台原因整单退还 = 剩余完整年数 × 年费 × **实付折扣系数**(下单时快照,避免后台调系数后对不上)。用户端不提供退款入口,退款只由后台发起(PRD 8.3.1)。
- **每日对账**:定时任务拉取微信账单与本地订单比对,差异进入后台对账队列。
- **只维护一个价格锚点**:多年价按系数现算,不另存第二套价格(PRD 8.3.1)。

**佣金与运营商**:

- 订单支付成功事件 → 生成佣金流水:首单 / 续费比例从配置读取(初始 30% / 10%)并写入流水快照。
- **红线写进数据结构**:运营商只有 `referrer_operator_id` 单列,没有上级字段、不能自建下级,从 schema 上杜绝多级分销(PRD 7.3、10.4.3)。
- 月结:佣金结算单状态机「待结算 → 已结算 → 已打款」,打款后不可撤销,纠错走线下凭证。
- 年度保底任务(≥50 个付费会员或 ≥3 个落地项目)由事件累计,在后台与运营商「业绩概览」展示进度。
- 保证金(¥10,000,可退)属预收款,单独台账,不与收入混记。

### 6.3 消息系统

**一期:增量同步,不做实时 IM**(PRD 5.5.5):

- 同步协议:客户端带 `cursor` 拉取;服务端按会话自增序号返回增量;前台 3 秒轮询,页面隐藏/无新消息时指数退避,降低无效请求。
- **未读数 = 会话最大序号 − 已读游标**,存 PG,天然幂等,无需 Redis 计数器与对账。
- 单聊会话以 `(min(uid), max(uid))` 唯一,与消息列表同一套会话(PRD A9);猫立方每个项目一个群聊、内部工作安排一个群聊。
- **订阅消息授权额度**:微信订阅消息是用户逐次授权,设 `subscribe_quota(user, template, remaining)`;在「关注 / 加入猫立方 / 提交任务」等**上下文动作**处申请授权,发送时消耗额度;无额度则降级为站内未读,并在下次进入小程序时提示开启提醒。
- **圈内通知合并**:同圈同自然日只发一条并累计条数。用 `circle_digest(circle_id, date, count)` 做 upsert 计数,由日结任务统一发送,避免「先判断再自增」的并发竞态。
- 内容安全:聊天消息异步检测,命中违规撤回并记分(见 6.5)。

**二期:WebSocket 作为「加速通道」**,而不是替代。服务端有新消息时只推一个轻量提醒,客户端收到后仍走同一套增量同步接口,因此断线、重连、离线补拉没有第二套语义。`Realtime` 适配器默认空实现,上线 WebSocket 时再装载。

### 6.4 搜索与匹配

**统一选项体系**:PRD 9.1 指出「合作需求」与「合作提供/主要交付」必须用同一套选项才能做交集。因此建 `taxonomy`(行业、区域、需求/供给、主体类型等),以 `code` 为键,**只停用不删除**,所有画像字段存 code,而不是文本。

**搜索**:一期使用 PostgreSQL(pg\_trgm / 中文分词扩展,取决于云 RDS 是否支持);通过 `Search` 适配器抽象,内容量或查询复杂度上来后切换 Meilisearch/ES,索引通过 outbox 事件增量同步。

**匹配(事业线)**:

1. **先给后要**(PRD 9.1):注册后立刻按粗标签给 3 条结果,再引导完善画像;画像未填全时展示热门推荐。
2. **预计算 + 在线重排**:画像更新事件触发后,按「区域 / 行业 / 标签」倒排求交得到候选,再按公式打分,把每个用户的 Top-K 写入 `match_candidates`;首页读取预计算结果,保证首屏 ≤ 3 秒。
3. **评分公式配置化**:需求-供给互补 40%、行业 25%、区域 20%、身份互补 15%,权重在后台可调并保留版本。同分按会员等级(企业版 > VIP > 普通),**不另设推荐位或插队**(PRD 8.3.1)。
4. **可解释**:规则就能生成理由模板(「你需要 X,对方提供 X」),不依赖 LLM;LLM 只用来润色。
5. **AI 增强(二期)**:用 pgvector 对简介等文本做向量相似度,作为第五个可开关维度加入加权;通过 A/B 与采纳率(点击、收藏、联系)评估再扩大。

### 6.5 内容安全与审核

```text
用户提交 → 敏感词前置过滤(本地,后台可维护)
        → 文本:同步机器检测;命中→拦截并提示,记违规
        → 图片/音视频:异步检测;回调前内容状态=审核中(图片占位),通过→展示中,命中→自动下架
        → 展示中 → 用户举报 → 人工复核(24 小时内)→ 属实:下架 + 记分(3 次限制发布 7 天)→ 严重者封号
```

- 通过 `Moderation` 端口封装微信内容安全接口(文本、图片、音视频),**接口版本、参数与场景值以微信官方最新文档为准**,不把具体调用写死在业务代码里;后续可叠加腾讯云 IMS 等增强实现。
- 与 PRD 状态机对齐:内容「审核中 → 展示中 → 已下架」;已下架不可自行恢复,可申诉。
- **统一审核任务表 `review_tasks`**:来源包括机器命中、用户举报、认证材料、高风险类目抽检(金融/医疗/政府项目),后台一个队列、按 SLA 排序处理。
- **AI 辅助审核(可选)**:对举报与高风险内容做预分类、摘要与风险提示,提高审核员效率;**不自动处罚**,处罚必须人工确认。
- 合规遵守:不得引导站外交易——聊天与发布内容检测「加我微信 / 私下联系」等引流词,命中先提示再记分(词库后台可维护)。

## 7. AI 能力层(重点)

### 7.1 原则

1. **可选、可降级**:每个 AI 功能有开关、超时和人工路径。AI 失败 = 回到原有表单,不是报错。
2. **人在回路**:AI 只给「草稿 / 建议」,用户确认后才落库、才发布。
3. **隐私最小化**:手机号、证件号、联系方式不进入提示词与向量;发送前做脱敏;外部模型调用记录审计。
4. **不新增页面**:AI 入口嵌在已有的入驻、发布、搜索、猫立方页面中,符合 PRD「尽量从简」。
5. **可评估、可控成本**:记录采纳率、修改率、延迟、成本;按用户/功能配额,超额自动降级。
6. **模型可替换**:`LLM / Embedding / OCR / ASR` 都是端口,供应商可切换;使用境内服务时需评估生成式 AI 相关备案与合规要求(见第 12 章)。

### 7.2 AI 网关(`ai` 模块)

统一承担:提示词模板与版本管理、**结构化输出**(JSON Schema 校验,不合规则重试或降级)、超时/重试/熔断、相同输入缓存、用量计量与配额、脱敏、审计日志、与 taxonomy 的 code 映射(模型只能输出合法选项,否则丢弃)。业务模块只调用 `ai.Facade`,不直接接触任何厂商 SDK。

### 7.3 场景矩阵

| # | 场景 | 用户操作变化 | 实现要点 | 降级方式 | 阶段 |
| --- | --- | --- | --- | --- | --- |
| 1 | **一句话入驻** | 说/写一段话,或拍名片、营业执照,自动填好第二层画像 5 项(区域、行业、需求、提供、简介),用户只确认 | LLM 抽取 + OCR;输出映射 taxonomy code | 原表单 | 一期 |
| 2 | **发布智能草稿** | 粘贴一段文字/海报/链接,自动生成对应类型的独立字段草稿 + 供需标签 + 领域标签 | 四类发布表单字段各自独立(PRD 8.5),按类型选模板 | 手动填写 | 一期 |
| 3 | **自然语言搜索** | 输入「杭州做新能源电池回收的服务机构」,自动转筛选条件 + 关键词 | LLM 转结构化查询;不信任模型输出,必须经 taxonomy 校验 | 关键词搜索 | 一期 |
| 4 | **智能客服** | 个人中心提问即得回答 | 基于规则文档的 RAG | 人工客服(9:00–18:00) | 一期 |
| 5 | **推荐理由与破冰语** | 看到「为什么推荐」;会员点「联系Ta」时给出首句建议 | 规则模板 + LLM 润色 | 仅规则理由 | 二期 |
| 6 | **语义匹配** | 事业线更准 | pgvector 向量相似度作为可开关的第五维 | 纯规则分 | 二期 |
| 7 | **猫立方协作** | 群聊/会议纪要一键生成任务草稿(负责人、确认人、截止);项目进度摘要;圈内一件事「到猫立方里办」自动生成项目草稿 | 抽取 + 摘要;结果经用户确认 | 手动建任务 | 二期 |
| 8 | **圈内需求整理** | 发布需求自动归类、打标签、到期前提醒续期 | 同 2 | 手动 | 二期 |
| 9 | **审核辅助** | 审核员看到预分类与摘要 | 见 6.5 | 原队列 | 一期/二期 |
| 10 | **运营洞察** | 运营用自然语言查看漏斗、转化、异常(刷量/批量注册) | 只读视图 + 受限查询;异常检测先用规则与统计 | 固定看板 | 三期 |

> **范围提示**:PRD 0.1 要求避免低权重需求。场景 1\~4 的定位是「替代填表的辅助入口」,不新增页面与业务规则,但仍属需求范围变化,**建议产品确认后再纳入一期**;若暂不纳入,架构上只需保留 `ai` 模块未装载。

### 7.4 AI 对体验的具体改进

- **入驻转化**:PRD 9.1 的三层画像里,第二层 5 项是匹配的前提,也是流失最高的环节。「一句话入驻」把它从多个下拉框变成一次说话,配合「先给后要」的 3 条结果,让用户在 1 分钟内看到价值。
- **发布效率**:四类内容字段各自独立,字段多。草稿生成把「从零填写」变成「检查修改」。
- **找人效率**:自然语言搜索对应一期主场景「找对人 + 联系上」(PRD 1.4.1),不依赖匹配算法即可提升命中。
- **协作效率**:把猫立方里的聊天沉淀为任务与进度,这是「让合作有流程、有留痕」(PRD 1.1)的直接落点。

## 8. 交互体验与开放能力

### 8.1 小程序体验设计

| 目标 | 做法 |
| --- | --- |
| 首屏 ≤ 3 秒(PRD 10.4.2) | 首页单次聚合接口(BFF 一次返回卡片流 + 画像进度 + 未读数);读 `match_candidates` 预计算结果;分包加载;图片走 CDN 并生成缩略图;骨架屏 |
| 列表流畅 | 每页 20 条游标分页;乐观更新(关注、收藏);「换一批」读下一批候选,不重算 |
| 渐进式画像 | 第一层只有手机号、身份类型、名称,不出现下拉框;第二层按「一次补 1\~2 项」分次采集;完成度进度条 + 「还有 N 条更匹配资源」(PRD 9.1) |
| 少填表 | 入驻、发布页顶部固定一个「说一句话,帮我填」入口(第 7 章场景 1/2),AI 失败或未开启时入口隐藏,表单照常 |
| 授权时机 | 订阅消息在用户做「关注 / 加入猫立方 / 提交任务」时顺带请求,而不是启动时一次弹出 |
| 状态可见 | 所有受限能力返回 `Reason`,前端展示「为什么不能做 + 怎么解锁」(开通会员、完成实名等) |
| 错误与空状态 | 统一错误码与文案;游客进入消息页显示空状态而非报错(PRD 3.1) |
| 合规入口 | 举报、隐私政策、账号注销入口固定位置;首次启动取得隐私同意 |

### 8.2 接口契约

- **OpenAPI 3 作为单一事实源**:后端注解/契约先行,自动生成小程序 TypeScript 客户端与后台 Admin 客户端,减少前后端联调返工。
- 版本策略:`/api/v1`;破坏性变更新开版本,旧版本保留一个发布周期。
- **幂等键**:所有创建与支付类接口支持 `Idempotency-Key`。
- 统一响应、错误码、分页与 `request_id`。

### 8.3 开放架构(二期)

- **开放 API**:同一份 OpenAPI 对外裁剪;OAuth2 client-credentials 或 API Key + 签名;按应用限流与配额;字段白名单默认**不含联系方式**。
- **Webhook / 事件出口**:复用 Outbox 事件,按订阅投递(`ContentPublished`、`OrderPaid`、`ReportConfirmed` 等),带签名与重试。
- **扩展点**:`Moderation`、`Pay`、`Notify`、`LLM`、`Search` 等端口即扩展点,新增供应商 = 新增适配器,不改业务模块。

## 9. 可靠性、运维与交付

### 9.1 高可用方案

PRD 目标可用性 ≥ 99.5%(约每月 3.6 小时停机预算),且明确不构成硬性 SLA。据此分档:

| 层 | S0 | S1(正式运营推荐) | S2 |
| --- | --- | --- | --- |
| 应用 | 1 实例 | api × 2、worker × 1,滚动发布 | K8s + HPA,按模块拆分 |
| 数据库 | 单实例 + 每日全备 + WAL 归档(PITR) | 托管 PostgreSQL 主从,自动故障转移 | 读写分离,热点表分区 |
| 缓存 | 进程内 | Redis 主从/哨兵 | Redis 集群 |
| 异步 | PG 任务队列 | PG 任务队列 | NATS / RabbitMQ |
| 存储 | OSS | OSS | OSS 跨可用区/跨区域复制 |

- **备份目标**(建议值,需研发与业务确认):RPO ≤ 5 分钟(WAL 归档)、RTO ≤ 1 小时;每季度做一次恢复演练。
- **降级矩阵**:AI 不可用 → 原表单;搜索适配器故障 → 回退 PG 简单检索;微信内容安全接口超时 → 文本发布走「审核中」队列重试,不放行;Redis 不可用 → 回退进程内缓存/限流,仅降低一致性与性能。
- **优雅停机、健康检查**:`/healthz`(存活)、`/readyz`(依赖就绪),停机时先摘流量再排空任务。

### 9.2 发布与变更

- **数据库迁移**:expand → migrate → contract 三步兼容,迁移向前兼容、可回滚;迁移作为独立角色/步骤执行。
- **灰度**:用**特性开关**按用户比例/白名单放量,取代 Argo Rollouts;K8s 阶段使用原生滚动更新 + 就绪探针即可。
- **配置变更**:业务参数改动写审计、可回滚、不需要发版(见 9.4)。

### 9.3 可观测性

- 统一使用 **OpenTelemetry**(日志、指标、链路同一套埋点),后端可选 Prometheus + Grafana、云监控;日志结构化,带 `request_id`、`user_id`(脱敏)、`module`。
- 关键业务指标看板:注册、画像完成度、匹配点击、联系发起、会员转化、支付成功率、猫立方开通数、审核积压。
- 告警(初始值,可配):P99 > 3s、错误率 > 1%、支付回调失败 > 0、审核 SLA 即将超时、AI 采纳率骤降或成本异常。
- **审计**:退款、封禁、改配置、查看联系方式、导出对账等写独立审计表,追加写。

### 9.4 三层配置(满足 PRD「一律后台可配、不得硬编码」)

| 层 | 内容 | 机制 |
| --- | --- | --- |
| 启动配置 | 端口、数据库、密钥引用、`modules.enabled`、`adapters.*` | 配置文件 + 环境变量 + 密钥管理 |
| 业务配置 | 会员年费、折扣系数、订阅价格、佣金比例、全部限额(PRD 11.5)、匹配权重、敏感词、taxonomy、主体类型 | `settings` 表:带类型校验、版本号、生效时间、操作人审计;变更发事件使缓存失效;后台一处维护 |
| 特性开关 | AI 各场景、WebSocket、新匹配算法、灰度比例 | `feature_flags` 表,支持按用户/比例/白名单 |

### 9.5 安全与交付流程

- **CI 门禁**:单元测试、模块边界检查、依赖漏洞扫描、静态安全扫描(SAST)、迁移检查。
- **上线前**:渗透测试、越权测试(以 PRD 权限矩阵为准)、支付回放与幂等压测、联系方式抓取压测。
- **数据库连接**:SSL + 证书校验;应用使用最小权限账号,迁移与后台使用独立账号。
- **WAF/限频**:接入层按 IP、用户限频;联系方式查看、短信验证码、搜索额外加严。

## 10. 工程结构与测试

### 10.1 目录结构(精简)

```text
catcube/
├── cmd/catcube/              # 唯一入口:serve / migrate / jobs 子命令
├── kernel/                   # 平台内核
│   ├── module/               # 模块注册、拓扑装载
│   ├── config/               # 三层配置、feature flag
│   ├── eventbus/             # Outbox + 订阅
│   ├── scheduler/            # 到期转态、定时任务
│   ├── statemachine/         # 声明式状态机引擎
│   ├── policy/               # 授权策略
│   ├── audit/ obs/ crypto/
├── ports/                    # 能力端口(接口定义)
│   └── cache queue search vector storage pay moderation notify realtime llm
├── adapters/                 # 端口实现:pg / redis / nats / meili / wechat / oss / ...
├── modules/                  # 业务模块,每个模块内部三层
│   ├── identity/ profile/ content/ match/ circle/ cube/ msg/ trade/ trust/ ai/
│   │   ├── facade.go         # 对外接口 + 事件定义(唯一对外可见)
│   │   ├── transport/        # HTTP handler(仅解析/校验/序列化)
│   │   ├── app/              # 用例编排(事务、事件)
│   │   ├── domain/           # 领域模型、状态机、规则
│   │   └── infra/            # 仓储实现(经 ScopedRepo)
├── api/                      # OpenAPI 契约 + 生成代码
├── migrations/               # 迁移脚本(按模块分目录)
├── deploy/                   # compose / helm / K8s manifests
└── docs/
```

相比 v1.0:去掉独立的 `service` 与 `usecase` 重复层,统一为 `transport → app → domain → infra`;只有一处 middleware;所有可替换能力集中在 `ports/` 与 `adapters/`。

## 附录 A:v1.0 → v2.0 变更对照

| 项 | v1.0 | v2.0 | 理由 |
| --- | --- | --- | --- |
| 服务形态 | 12 个微服务 | 10 个模块的模块化单体,三档部署 | 契合万级用户规模,保留拆分能力 |
| 服务发现/配置中心 | Consul + Nacos | 配置文件 + DB 配置表;K8s 原生 | 少两个中间件 |
| 网关 | Kong / APISIX | 应用内中间件;云网关/Ingress | 不自建 |
| 消息队列 | RabbitMQ(必选) | Outbox + PG 任务队列(默认),可换 NATS/RabbitMQ | 默认零新增依赖 |
| 搜索 | ES(一期) | PG 内置检索,可换 Meilisearch/ES | 数据量小 |
| 向量 | 独立向量数据库 | pgvector | 同库、易运维 |
| 日志/链路 | ELK + Jaeger + Prometheus | OpenTelemetry,后端按需 | 一套埋点 |
| 灰度 | Argo Rollouts | 特性开关 + 滚动更新 | 更简单且更细粒度 |
| 权限 | Casbin(模型有误) | 能力 + 资源角色 + 状态门,表驱动测试 | 与 PRD 同构 |
| Token | 内嵌会员/角色 | 仅身份 + 权限版本号 | 无陈旧窗口 |
| 手机号 | 加密(不可检索) | 加密 + HMAC 盲索引 | 支持唯一校验 |
| 分摊支付 | 分账方案与 PRD 冲突 | 多笔认筹付给平台,不分账 | 与 PRD 8.3.1 一致 |
| 未读数 | Redis 计数器 | 序号 − 已读游标(PG) | 幂等、免对账 |
| 通知合并 | 先判断再自增(竞态) | 日结 upsert 计数 | 无并发问题 |
| AI | 二期外挂,三处孤立描述 | AI 网关 + 十类场景 + 降级机制 | 回应「减少复杂操作」 |
| 到期转态/配置/注销/留存 | 缺失 | 第 5、6、9 章补齐 | 落实 PRD 硬性规则 |
